# Spring Boot API Documentation Standards

Last updated: 2026-09-17

For Spring Boot, the standard is OpenAPI 3.1 generated by springdoc-openapi, with annotations filling in what the code cannot say: summaries, error shapes, examples, and security. The annotations are documentation, so treat them with the same review standards as code.

## Setup

- Use springdoc-openapi 2.x for Spring Boot 3.x. Configure an `OpenAPI` bean centrally for title, version, and security schemes rather than repeating them per controller.
- Split specs by API group (public v1, v2, internal) so internal endpoints never leak into the public spec. Internal endpoints get `@Hidden` or their own filtered group.
- Disable the interactive UI in production and serve a static spec instead. The spec is a build artifact; generate it in CI so it is reproducible and diffable.

## Annotation patterns

- **`@Tag` on controllers.** Group operations by domain (orders, payments), not by class name. Keep tag names consistent across controllers.
- **`@Operation` on every endpoint.** Short summary under 120 characters, a longer description with the use case, and an explicit `operationId`. The summary is what consumers read in the generated SDKs.
- **`@Parameter` on every parameter.** Description plus example. For complex query objects (filters, pagination), use `@ParameterObject` to keep controllers clean while documenting every field.
- **`@ApiResponse` for every non-200 response.** Document 4xx error shapes with the same care as success responses; this is where most API docs fail. Include 5xx only when the caller can act on it differently from a generic failure.
- **`@Schema` on DTOs.** Description and example on every field that is not self-evident. Complex generics and polymorphic types need explicit `@Schema` plus a discriminator mapping; do not trust inference there.
- Let validation annotations do their job. `@NotNull`, `@Size`, `@Pattern` flow into the schema automatically, so the contract and the code stay consistent for free.

## Error responses and problem details

- Standardize on RFC 7807 `ProblemDetail` for all error responses. Spring Boot 3 (built on Spring Framework 6) has built-in support; use it rather than a custom error envelope.
- Reference the shared problem schema from every `@ApiResponse` that documents an error. One error shape across the whole API means consumers write one error handler.
- Document what each error code means in business terms ("409 when the order is already paid", not "conflict"). The HTTP status says what happened; your description says why.

## Versioning the docs

- Put the version in the OpenAPI `Info` and keep separate spec groups per version. Never mutate a published version's spec; add a new one and deprecate the old.
- Mark retiring endpoints with `@Operation(deprecated = true)` and add `Deprecation` and `Sunset` headers. An annual review retires deprecated endpoints and removes orphaned schemas.
- Never put real customer data in examples. Review examples like you review test fixtures.

## Contract testing alignment

- The spec is a contract, not a sketch. Run oasdiff in CI against the production spec and break the PR on breaking changes.
- Generate consumers (SDKs) from the spec in CI rather than hand-writing clients. If the generated SDK compiles and the contract tests pass, the docs and the code agree.
- Validate at least one sample response per endpoint against the schema in tests. This catches the classic drift: code changed, annotations did not.
